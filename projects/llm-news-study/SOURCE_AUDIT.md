## 3. Model, timing and storage claims

- **Gemma cutoff:** Google's [model card](https://ai.google.dev/gemma/docs/core/model_card_4) and [Gemma Team technical report v2, section 2.4](https://arxiv.org/html/2607.02770v2) state January 2025 for pretraining. Section 3 describes instruction tuning; the inspected passages do not certify an equivalent cutoff for every later training stage. A 90-day margin is a proposed heuristic, not proof of decontamination. If using January 31 conservatively, adding 90 days reaches May 1, 2025, not April 1. Keep this in a future study profile, not in the collector API.
- **Market alignment:** [exchange_calendars](https://github.com/gerrymanoim/exchange_calendars) exposes dated session opens/closes. An actual exchange schedule must determine the boundary; 16:00 is not universal. Validate US examples against the [Nasdaq 2026 calendar](https://beta.nasdaqtrader.com/Trader.aspx?id=Calendar), including the 13:00 early close on November 27. Session assignment alone does not establish a valid return-label interval.
- **DuckDB concurrency:** [Current documentation](https://duckdb.org/docs/2.0/connect/concurrency) distinguishes embedded access from server arrangements. A direct embedded writer plus an independent dashboard reader is not the documented native-file mode. Multi-process solutions exist, but add machinery. SQLite is a better initial operational fit; DuckDB can analyze exported snapshots.
- **SQLite WAL:** [Official documentation](https://www.sqlite.org/wal.html) supports readers alongside a writer on local storage, with one writer at a time and bounded transactions. It also identifies a WAL race fixed in 3.51.3, with specified backports. Verify the runtime's actual SQLite version and use a fixed release/backport; do not assume the Python version establishes the SQLite version. Keep live databases off network/synchronization folders.
- **Streamlit:** [Its execution model](https://docs.streamlit.io/develop/concepts/architecture/session-state) reruns scripts on interaction and session state is not a durable job queue. Store jobs, progress and labels in the database; run collection outside page execution.
